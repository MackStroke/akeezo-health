# Build guide

## Working method

Use this as a repository specification. Begin with README and skill.md; then routes, design and architecture. Implementation prompts are staged in implementation-prompts.md. If a repository already exists, inspect and adapt it first. Do not overwrite unrelated code or switch its working integrations unnecessarily.

## Build sequence

1. **Inventory:** map existing routes/assets/integrations, capture current Akeezo URL migration needs, select supported versions and create the implementation traceability table.
2. **Foundation:** scaffold React/Express/TypeScript/MongoDB with SSR, shared contracts, environment validation and test replica set. Deliver one server-rendered dynamic route and 404.
3. **Visual shell:** tokens, official logos, home/inner header, footer, planning CTA, hero/search and cards. Match homepage and hospital directory before implementing other pages.
4. **Content lifecycle:** schemas, revisions, route registry, admin sessions/roles, private preview, publish/unpublish/restore and delivery jobs. Verify one complete home edit end to end.
5. **Catalogue:** treatments/procedures, hospitals/doctors, destinations/cities, all list/detail templates, filter/pagination/search, gallery and comparison.
6. **Conversion:** calculator, planner, contextual enquiry, receipt/idempotency and restricted coordinator inbox. Add secure records only after access/upload controls work.
7. **Editorial and extended families:** blog/contributors, geographic guides, costs/safety/recovery, combined/comparison, galleries, packages/experiences, company/legal/support.
8. **Partners/community:** applications and review, scoped profile editing, moderated community. Feature-flag public exposure until real content/operations exist.
9. **Migration and QA:** aliases/canonicals, localization, responsive/visual tests, security and backups. Finish private staging and report remaining release gates.

## Avoid shortcuts

Do not build only the homepage and call the site complete. Do not use hardcoded copies of every provider. Do not make all detail pages the same generic template. Do not make admin controls localStorage-only. Do not show form success before persistence. Do not hide missing functionality behind buttons that do nothing. Do not create generated patient outcomes or invented accreditation badges. Do not publish 26,226 blank SEO pages to match the sitemap count.

## Assets and business inputs

Logo source URLs and brand tokens are documented. Confirm exact SVG files before final visual signoff. Use safe private fixtures while obtaining provider data, current price rules, consented media, team details and policy content. Missing approved data blocks the affected public module, not unrelated coding work.

## Review checkpoints

After foundation: demonstrate SSR HTML, 404 and MongoDB connectivity. After visual shell: desktop/mobile screenshots with measured comparison notes. After CMS: demonstrate draft isolation, publish, conflict and restore. After conversion: show a stored test receipt and notification failure recovery. Before delivery: route matrix, permission tests, link crawl, private preview and actual test results.

## Handoff prompt

Paste the first prompt from implementation-prompts.md with this folder attached. Tell the coding agent to continue through the stages within authorized scope, maintain a progress checklist and avoid repeated approval questions for reversible local implementation. Public rollout remains a separate final decision.
